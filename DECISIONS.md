# DECISIONS — принятые решения и почему

> Правило: перед тем, как менять что-то фундаментальное (стек, структуру данных, стиль карты и т.д.), проверь — нет ли уже записи здесь. Если решение меняется — не удаляй старую запись, допиши новую с пометкой "заменяет решение от [дата]".

## Карта
- **Движок:** MapTiler (не Mapbox). Причина: у основателя только российская банковская карта, Mapbox требует привязку карты для активации даже бесплатного тарифа; MapTiler даёт бесплатный доступ по email без карты.
- **Стиль:** MapTiler Streets (яркий, живой), не стандартный OpenStreetMap-стиль (слишком жёлтый/пустынный на вид — было явное замечание основателя).
- **3D:** через MapTiler SDK JS (на основе MapLibre GL), рельеф включается через `setTerrain`, доступен как переключаемый режим, не основной вид по умолчанию (тяжелее для слабых устройств).

## Карта на фронтенде (дата: 2026-09-14)
- MapTiler SDK JS подключается **UMD-сборкой с CDN** (jsdelivr `@maptiler/sdk@1.2.0`), без npm/сборщика — фронтенд статический (простая связка).
- **API-ключ не в JS**: страница отдаёт `<div id="map" data-maptiler-key="{{ maptiler_api_key }}">`, JS читает атрибут. Ключ приходит из `MAPTILER_API_KEY` (settings/env), не хардкодится.
- Изображения (фото мест) для API отдаются **абсолютными URL** (`request.build_absolute_uri`), т.к. он же рендерит карту клиентским JS.
- Список мест отдаётся из бэкенда через DRF **частично уже по-русски**: расстояние/сортировка «ближайшие места» считаются на сервере (haversine в Python, без PostGIS — в духе решения про координаты), `distance_km` приходит клиенту. Фильтр по категории — `?category=<code>`.

## Маршруты (дата: 2026-09-14)
- **Простые маршруты** (N ближайших точек) — расчёт на сервере: haversine от старта, сортировка, leg-дистанции между соседними точками, `total_km`; клиент — API `/api/route/simple/?lat&lng&limit`, полилиния + панель на карте.
- **Многодневные маршруты** — модель `Route` (мультиязычные название/описание, регион, `duration_days`) + `RouteStop` (место, `day`, `order`, `minutes`, `note`). Курируются волонтёрами/админом, проходят лёгкую модерацию (`check_route`). API `/api/routes/` и `/api/routes/<id>/` (дни → стопы). Auto-факт: `Route.total_km` = сумма хаверсин-дистанций между соседними стопами по порядку.
- **Навигация по дорогам/тропам** — на MVP **публичный OSRM-demo `router.project-osrm.org`** (данные OSM) через **серверный прокси** (`kuhiston/routing.py`, urllib, таймаут 6с): фронт не зависит от CORS и ключей, URI-profile `driving|foot|bike`. При недоступности сервиса — **фолбэк по прямой** (хаверсин × 1.3, 15 мин/км) с пометкой в ответе `source: fallback`.
- **Self-hosted OSRM** (docker + сборка OSM по Таджикистану) — продакшн-задача на машине основателя (не в песочнице), в TASKS.md помечено как задача за пределами MVP-сэндбокса (см. ISSUES.md).

## Бэкенд
- **Django + Django REST Framework (DRF)** — финальный выбор (заменяет открытый вопрос от Этапа 0, дата: 2026-09-13). Причины:
  - Встроенная админка из коробки — готовая панель для волонтёров/админа (это прямое требование Этапа 1 «Wеб-панель»).
  - Встроенный i18n на три языка (ru/en/tg) — задача «Настроить i18n-инфраструктуру» решается штатным механизмом Django.
  - Встроенная аутентификация и роли пользователей.
  - ORM + миграции — модель данных из раздела 5 PROJECT.md описывается без лишней обвязки.
  - `django.contrib.gis` — родная интеграция с PostGIS для геозапросов.
  - DRF — для API, которое будет потреблять фронтенд (карта, списки мест, маршруты).
  - У основателя уже есть опыт с Python.

## База данных
- PostgreSQL + PostGIS. Причина: нужны геозапросы (ближайшие точки, маршруты).
- **Важное техническое ограничение (дата: 2026-09-14):** PostGIS-движок Django (`django.contrib.gis.db.backends.postgis`) и приложение `django.contrib.gis` требуют GEOS + GDAL на стороне Python-приложения, иначе Django не стартует с ошибкой `ImproperlyConfigured: Could not find the GDAL library`. Поэтому:
  - По умолчанию приложение работает на стандартном `django.db.backends.postgresql` движке (не требует GEOS/GDAL), БД содержит PostGIS-расширение.
  - PostGIS-движок Django включается флагом `USE_POSTGIS_BACKEND=1` на машине/сервере, где установлены GEOS+GDAL (например, через Docker-образ бэкенда).
  - `django.contrib.gis` НЕ добавлять в `INSTALLED_APPS`, пока не понадобятся GIS-фичи — он тоже требует GDAL при импорте.

## Хостинг
- Бюджета на старте нет — бесплатные тарифы.
- **База данных: Neon Free** (дата выбора: 2026-09-14). Причины:
  - Бесплатно без срока (нет 30-дневного ограничения как у Render Postgres).
  - 0.5 ГБ хранилища, 100 CU-часов вычислений в месяц — достаточно для MVP.
  - PostGIS доступен как расширение в БД (включается одной командой).
  - Автоматическое scale-to-zero → при простое приложение потребляет $0.
- **Приложение (Django): Render Free** (дата выбора: 2026-09-14). Причины:
  - Бесплатный веб-хостинг с авто-деплоем из Git.
  - 750 часов в месяц, спин-даун после 15 минут простоя — нормально для previews/MVP.
  - Важно: Render Postgres Free БЕЗОПАСНО использовать НЕЛЬЗЯ (данные стираются через 30 дней) — для БД всегда Neon.
  - GEOS+GDAL (нужны для PostGIS-движка Django) ставятся через Dockerfile/requirements на Render.
- **Локальная разработка: Docker Compose** (`docker-compose.yml` в корне проекта) — `postgis/postgis:16-3.4` образ, PostGIS доступен из коробки.

## Монетизация
- Без цели извлечения прибыли. Только: платное продвижение в топе выдачи для бизнесов (отели/рестораны/гиды) + добровольные донаты. Никакой навязчивой рекламы, никакой комиссии с бронирований на старте.

## Модерация
- Первый уровень — список запрещённых слов (ru/en/tg), не ИИ. ИИ-модерация — отложенная задача, добавляется после достижения ~1000 пользователей.

## Бронирование
- MVP — заявки без онлайн-оплаты, подтверждение вручную владельцем места. Онлайн-оплата — будущий этап, не блокирует MVP.

## Языки
- Три языка с самого старта: русский, английский, таджикский — заложить i18n-архитектуру сразу, не хардкодить текст.

## Лёгкая модерация (дата: 2026-09-14)
- Черновой список запрещённых слов на трёх языках — в `kuhiston/moderation.py` (по PROJECT.md раздел 10). Подлежит утверждению основателем.
- Проверка при **сохранении места в админке** (`PlaceAdmin.save_model`): если запрещённое слово найдено в названии/описании на любом языке → статус принудительно становится `rejected` (даже если волонтёр пытался поставить `published`). Чистое место сохраняет статус `pending` (ждёт модератора).
- Поиск — подстрока без учёта регистра (ловит словоформы: «грабёж» в «грабежами»). Допустимы редкие ложные срабатывания — будут уточнены финальным списком слов; ИИ-модерация — только после ~1000 пользователей.

## Волонтёрская веб-панель (дата: 2026-09-14)
- **Django-админка**, ограниченная группой «Волонтёр»: волонтёр видит только раздел «Места» (добавление/изменение), раздел «Категории мест» и «Регионы» (только просмотр). Пользователи, бронирования, отзывы — скрыты (403 Forbidden).
- Группа и права создаются data-migration (`users.0002_volunteer_group`), не при каждом запуске.
- При сохранении нового места `PlaceAdmin.save_model` **автоматически проставляет `added_by = request.user`** (если не задан). Статус модерации по умолчанию `pending` (из модели).
- Волонтёр **не может публиковать** места в обход модерации (статус `moderation_status` не скрыт, но default=pending; полноценная модерация — следующая задача).

## Модель «Отзыв/рейтинг» (дата: 2026-09-14)
- `Review`: FK на место + FK на автора (`AUTH_USER_MODEL`, турист). Оценка 1–5 с валидаторами И `CheckConstraint` на уровне БД (отзыв с оценкой 6 не запишется даже в обход формы).
- Средний рейтинг и число отзывов — вычисляемые свойства на `Place` (`average_rating`, `reviews_count`), не хранимые поля (считаются на лету; при росте числа отзывов можно кешировать).
- Текст отзыва — один `TextField` (автор пишет на своём языке, мультиязычные колонки не нужны).

## Модель «Заявка на бронирование» (дата: 2026-09-14)
- **Без онлайн-оплаты** (MVP): статусы `new → confirmed/rejected` или `cancelled` (отмена туристом).
- Турист — FK на `AUTH_USER_MODEL` (по разделу 3 PROJECT.md регистрация нужна для брони) плюс **снимок контактов** (`tourist_name`, `tourist_contact`) — заявка остаётся читабельной, даже если профиль меняется/теряется.
- Даты `check_in`/`check_out` (заезд/выезд), `notes`, `pay_on_site` (пометка «оплата на месте»).

## Модель «Объект для бронирования» (дата: 2026-09-14)
- **Категории** (`жильё/гид/транспорт/ресторан`) — расширяемая модель `BookingCategory` (код + названия на 3 языках), как и категории мест.
- **Связь с местами — M2M** (`BookingObject.places` → `Place`): один объект (например, гостевой дом) обслуживает несколько достопримечательностей; у места может быть много объектов. `related_name='booking_objects'`.
- Владелец — FK на `AUTH_USER_MODEL` (роль `place_owner`). Поля `is_active` и `is_promoted` (продвижение в топе — включается в админке вручную, Этап 7).
- Координаты — lat/lng (как у Place), контакты: телефон, email, сайт.
- Заявка на бронирование — отдельная следующая задача (своя модель, не смешана с текущей).

## Модель «Пользователь» (дата: 2026-09-14)
- **Кастомная модель `users.User` как `AUTH_USER_MODEL`** (наследует `AbstractUser`), а не профиль-приставка к стандартному User. Причина: роли нужны каждой модели (место, заявки, отзывы), и переопределить модель сейчас (в начале разработки) дешевле, чем позже.
- **Роли — поле `role` с фикс. набором TextChoices**: `tourist` (турист), `volunteer` (волонтёр), `place_owner` (владелец места), `admin` (администратор/основатель). Гость-незарегистрированный роли не имеет (он не User). Админ дополнительно = `is_superuser`. Хелперы `is_volunteer()/is_place_owner()/is_admin()`.
- Из-за смены `AUTH_USER_MODEL` базы пересозданы с нуля (на этой стадии БД не данные, а схема) — допустимо и зафиксировано в журнале. `Place.added_by` переведён на `settings.AUTH_USER_MODEL`.

## Модель данных «Место» (дата: 2026-09-14)
- **Мультиязычные поля** (название, описание, подпись фото): отдельные колонки на каждый язык (`name_ru`/`name_en`/`name_tg`). Без сторонних библиотек перевода (django-hvad/parler и т.п.) — проще, прозрачнее для SQL-запросов и фильтрации. Доступ к полю по языку — методы `get_name(lang)`/`get_description(lang)`.
- **Координаты хранятся как два `DecimalField` (latitude/longitude, 6 знаков ≈ 0.1 м)**, а не `PointField`. Причина (связано с ограничением PostGIS/GEOS-GDAL из соседнего раздела): `PointField` требует PostGIS-движка Django и GEOS+GDAL на стороне приложения — в песочнице и на обычном хостинге без этих библиотек модель не работает. Lat/lng-колонки работают везде. Гео-запросы «ближайшие места» на этапе MVP с небольшим числом мест — в Python (вычисление расстояния), при росте данных — поверх этих колонок в PostGIS (добавить сгенерированную geometry-колонку/индекс на машине с GEOS).
- **Категория места** — отдельная модель `PlaceCategory` (код + названия на 3 языках), чтобы список категорий расширялся без изменения кода (требование PROJECT.md раздел 5).
- **Фотографии** — отдельная модель `PlacePhoto` (FK, несколько штук на место), `ImageField` + Pillow, `MEDIA_ROOT` на `frontend/media`.
