# Kuhiston — туристическое приложение по Таджикистану

> Это мастер-документ проекта. Он не переписывается в процессе разработки — только дополняется, если появляются новые решения (в раздел "История изменений" внизу). Все агенты (в т.ч. OpenCode) обязаны прочитать этот файл перед началом работы, наравне с TASKS.md и PROGRESS.md.

## 1. Что мы строим

Веб-приложение (сайт, mobile-first дизайн, готовность стать PWA) для туристов, путешествующих по Таджикистану. Приложение определяет местоположение пользователя (или выбранную им точку) и показывает культурные, исторические и природные достопримечательности рядом, помогает строить маршруты между ними, и позволяет забронировать жильё, гидов, транспорт и рестораны рядом с этими местами.

Рабочее название: **Kuhiston** (временное — владелец продукта планирует сменить в будущем; название должно быть легко заменяемо — не хардкодить нигде, кроме одной конфигурационной константы/файла бренда).

Отсутствие цели извлечения прибыли: проект не должен быть перегружен монетизацией. Единственные источники дохода — платное продвижение (топ выдачи) для отелей/ресторанов/гидов, которые сами захотят платить за видимость, и добровольные донаты туристов. Никакой навязчивой рекламы, никакой комиссии с брони на первом этапе.

## 2. Основной пользовательский сценарий (MVP)

1. Турист открывает сайт.
2. Приложение определяет его местоположение (или он вводит его вручную/выбирает на карте).
3. На карте показываются ближайшие культурные/исторические/природные места.
4. Турист может:
   - увидеть карточку места (см. раздел 5)
   - построить маршрут до места (ближайшие точки, маршрут по дорогам/тропам, или выбрать готовый многодневный маршрут)
   - подать заявку на бронирование жилья/гида/транспорта/ресторана рядом
   - оставить отзыв/оценку (требует лёгкой регистрации)
5. Всё работает без интернета в офлайн-режиме для скачанного региона (карта + данные о местах).

## 3. Роли пользователей

- **Турист (гость)** — просматривает без регистрации. Регистрация нужна только для отзывов и бронирований.
- **Волонтёр** — региональный представитель, у которого есть логин/пароль от основателя. Добавляет новые места через веб-панель (скрытый раздел сайта). Публикация — после лёгкой модерации (см. ниже).
- **Владелец места** (отель/гостевой дом/гид/ресторан/транспорт) — подтверждает заявки на бронирование, может оплатить продвижение в топ выдачи.
- **Администратор (основатель)** — управляет волонтёрами, модерацией, платным продвижением.

## 4. Языки

Интерфейс должен поддерживать три языка с самого старта: **русский, английский, таджикский**. Архитектура — через файлы локализации (i18n), не хардкодить текст в шаблонах/компонентах.

## 5. Модель данных: "Место" (place)

Карточка места должна содержать:
- Название (на 3 языках)
- Описание (на 3 языках)
- Категория (историческое/культурное/природное/религиозное и т.д. — сделать расширяемым списком)
- Координаты (lat/lng)
- Регион (для офлайн-скачивания по регионам, см. раздел 8)
- Фотографии (несколько)
- Часы работы
- Входная цена (если есть)
- Сложность доступа (например: лёгкая пешая прогулка / нужен внедорожник / горный поход)
- Рекомендуемое время года / сезонность
- Рейтинг и отзывы туристов (после регистрации)
- Связанные объекты рядом (жильё/гиды/транспорт/рестораны — для бронирования)
- Статус модерации (на проверке / опубликовано / отклонено)
- Кто добавил (волонтёр) и когда

## 6. Маршруты

Нужны все три варианта (реализовать по очереди, начиная с самого простого):
1. **Ближайшие точки** — просто список/карта ближайших мест от пользователя (самое простое, делать первым).
2. **Готовые многодневные маршруты** — курируемые заранее (волонтёрами/админом) наборы точек с порядком посещения и примерным таймингом.
3. **Навигация по дорогам/тропам** — полноценный маршрут как в навигаторе (использовать роутинг-движок, например OSRM или аналог, работающий на данных OpenStreetMap).

## 7. Бронирование

Для MVP: **заявка внутри приложения без онлайн-оплаты**. Турист заполняет форму (даты, контакты, что интересует), заявка уходит владельцу места, он подтверждает/отклоняет. Позже добавить:
- опцию "оплата на месте" (просто пометка в заявке, не платёжный функционал)
- в будущем (не в MVP) — полноценную онлайн-оплату

Категории бронирования: жильё (гостевые дома, отели), гиды-экскурсоводы, транспорт/такси, рестораны.

## 8. Офлайн-режим

Критичен с самого начала. Подход: **скачивание карты и данных о местах по регионам**, которые пользователь выбирает сам (не вся страна сразу — экономия места на устройстве). Технически:
- Тайлы карты для офлайна нужно кэшировать/паковать по регионам (например, через MBTiles или аналогичный подход, совместимый с выбранным картографическим движком — см. раздел 9).
- Данные о местах (текст, категории, координаты) должны сохраняться в локальное хранилище браузера/устройства для выбранного региона.
- Фотографии — по возможности сжатые версии для офлайн-кэша, с возможностью догрузки оригиналов при наличии интернета.

## 9. Карта

- Библиотека/движок: **MapTiler** (уже есть API-ключ, будет передан отдельно, не хранить в открытом виде в публичном репозитории — вынести в переменные окружения).
- Стиль: яркий, живой (аналог MapTiler Streets), не блёкло-жёлтая стандартная OSM-плитка.
- Обязательна поддержка 3D-рельефа (особенно важно для горных регионов — Памир, Фанские горы) как переключаемый режим (2D по умолчанию для производительности, 3D по кнопке).
- Референс дизайна карты: связка тёмно-индиго + охра для брендовых элементов интерфейса (UI поверх карты), сама карта — живые "гугл-мапс"-подобные цвета.

## 10. Модерация контента волонтёров

MVP: **автоматическая лёгкая модерация по списку запрещённых слов** (на трёх языках) перед публикацией, либо публикация сразу с возможностью пожаловаться/скрыть. После достижения ~1000 пользователей — добавить модерацию через ИИ (отдельная будущая задача, не блокирует MVP).

## 11. Технический стек

- **Бэкенд:** Python — Django или FastAPI (решить на этапе архитектуры; Django — если нужна встроенная админка и ORM из коробки для волонтёрской панели; FastAPI — если важна скорость API и гибкость).
- **База данных:** PostgreSQL с расширением PostGIS (для геозапросов "ближайшие точки", маршрутов и работы с координатами).
- **Фронтенд:** веб (mobile-first, адаптивный дизайн), с прицелом на то, что позже потребуется мобильное приложение — по возможности не завязывать бизнес-логику намертво на веб-специфичные вещи.
- **Карта:** MapTiler SDK (для 3D) / MapTiler растровые тайлы (для 2D облегчённого режима).
- **Хостинг:** бюджета нет на старте — использовать бесплатные тарифы (например Railway, Render, или аналог с бесплatным tier для Postgres + бэкенда). Выбор — задача агента, зафиксировать решение в DECISIONS.md.
- **Локализация:** стандартный i18n-подход (файлы переводов на 3 языка, не хардкод).

## 12. Географический охват MVP

Вся страна сразу (не по регионам разработки) — но контента изначально может быть немного (волонтёры будут наполнять постепенно). Разбивка на регионы нужна для: (а) офлайн-скачивания карт, (б) организации волонтёров по областям.
